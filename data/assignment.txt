Взаимодействие процессов (потоков): взаимное исключение и синхронизация

1. Цель работы

Изучение механизмов взаимного исключения и синхронизации в операционной системе Windows, приобретение практических навыков организации согласованной параллельной работы процессов и потоков.

В ходе выполнения лабораторной работы необходимо:

-                изучить основные проблемы конкурентного доступа к общим ресурсам;

-                освоить системные объекты и функции Windows API для синхронизации;

-                реализовать модель взаимодействия процессов или потоков;

-                обеспечить корректный доступ к разделяемым ресурсам;

-                исследовать возникновение и предотвращение состояний гонки, взаимных блокировок и длительного ожидания;

-                оценить влияние механизмов синхронизации на производительность;

-                приобрести навыки экспериментального исследования многопоточных программ;

-                закрепить навыки применения системы контроля версий Git.

2. Теоретическая и методическая часть

2.1. Основные понятия

Перед выполнением лабораторной работы необходимо изучить:

1.    Конкурентное и параллельное выполнение процессов и потоков.

2.    Разделяемые ресурсы и совместный доступ к данным.

3.    Критический ресурс и критическая секция.

4.    Атомарность операций.

5.    Состояние гонки (Race Condition).

6.    Взаимное исключение (Mutual Exclusion).

7.    Взаимная блокировка (Deadlock).

8.    Голодание (Starvation).

9.    Приоритеты и справедливость обслуживания.

10.Активное и блокирующее ожидание.

11.Пропускную способность и время ожидания ресурса.

12.Основные модели синхронизации.

3. Общая постановка задачи

Разработать программное приложение, моделирующее конкурентную работу нескольких процессов или потоков с доступом к общим ресурсам.

Приложение должно обеспечивать:

1.    Создание участников модели.

2.    Изменение основных параметров моделирования.

3.    Использование механизмов синхронизации Windows API.

4.    Предотвращение некорректного совместного доступа к ресурсам.

5.    Отображение состояния участников.

6.    Регистрацию основных событий.

7.    Сбор статистики выполнения.

8.    Проведение экспериментов.

9.    Проверку корректности полученных результатов.

10.Корректное завершение всех процессов и потоков.

Приложение может быть консольным или оконным.

Основной язык реализации – C или C++ с использованием Windows API. Использование другого языка допускается по согласованию с преподавателем при условии непосредственной демонстрации соответствующих механизмов операционной системы.

Использование Sleep() в качестве единственного способа согласования работы участников не допускается. Вызов Sleep() разрешён для моделирования продолжительности операций и создания контролируемых задержек.

4. Общие требования к программной реализации

4.1. Параметризация

Основные параметры модели должны изменяться без модификации исходного кода.

В зависимости от варианта необходимо предусмотреть:

-                количество участников;

-                количество доступных ресурсов;

-                количество выполняемых операций;

-                продолжительность обработки;

-                интенсивность поступления запросов;

-                время ожидания ресурсов;

-                емкость очередей;

-                режим синхронизации.

Допускается задание параметров через консольное меню, аргументы командной строки либо конфигурационный файл.

4.2. Идентификация участников

Каждый участник модели должен иметь уникальный номер.

Для потоков необходимо предусмотреть вывод TID, для процессов – PID.

Пример:

WORKER 2 | TID=4820 | STATE=WAITING

4.3. Отображение состояний

Программа должна выводить основные состояния участников.

Пример для модели философов:

-                THINKING – размышление;

-                WAITING – ожидание ресурса;

-                EATING – использование ресурса;

-                FINISHED – завершение.

Изменение состояния должно регистрироваться в журнале событий.

4.4. Журналирование

Необходимо реализовать журнал основных событий программы.

Каждая запись должна содержать:

-                время события относительно начала эксперимента;

-                идентификатор участника;

-                тип события;

-                идентификатор ресурса или заявки, если применимо.

Пример:

[000125 ms] P2 WAITING RESOURCE=3

[000131 ms] P2 ACQUIRED RESOURCE=3

[000145 ms] P2 WORKING

[000153 ms] P2 RELEASED RESOURCE=3

Журналирование должно быть потокобезопасным.

Для измерения производительности допускается отключение подробного вывода, поскольку консольный вывод способен существенно влиять на результаты эксперимента.

4.5. Проверка корректности

Приложение должно содержать программные проверки условий корректности (инвариантов), соответствующих индивидуальному заданию.

Примеры:

-                один эксклюзивный ресурс не может одновременно принадлежать двум участникам;

-                читатель не должен получать несогласованное состояние данных;

-                количество заявок в ограниченной очереди не может превышать её емкость;

-                каждый элемент очереди должен обрабатываться согласно правилам модели;

-                после завершения всех участников не должно оставаться удерживаемых ресурсов.

В итоговом отчёте программы необходимо вывести количество нарушений инвариантов.

Корректная реализация должна завершать предусмотренные испытания без обнаруженных нарушений.

Отсутствие обнаруженных нарушений в нескольких запусках не является математическим доказательством отсутствия гонок. Студент должен дополнительно обосновать правильность применённого алгоритма синхронизации.

4.6. Обработка ошибок и завершение

Программа должна:

-                проверять результаты системных вызовов;

-                обрабатывать ошибки создания объектов синхронизации;

-                учитывать тайм-ауты ожидания;

-                освобождать захваченные ресурсы;

-                корректно завершать рабочие процессы и потоки;

-                закрывать системные дескрипторы;

-                предусматривать максимальную длительность эксперимента для предотвращения бесконечного зависания.

5. Индивидуализация экспериментальных данных

Каждому студенту назначается STUDENT_ID, соответствующий последним 3 цифрам студенческого билета.

Для индивидуальных экспериментов использовать:

SEED = 1000 + STUDENT_ID * 97

OPERATIONS = BASE_OPERATIONS + STUDENT_ID * 5

Значение BASE_OPERATIONS определяется стандартными параметрами варианта.

Студент обязан выполнить:

1.    Эксперимент со стандартными параметрами.

2.    Эксперимент с индивидуальными параметрами.

3.    Эксперимент с дополнительными параметрами преподавателя во время защиты.

Полученные результаты должны быть воспроизводимыми в пределах естественной вариативности времени выполнения.

6.2. Графическое представление

Обязательное требование: построить не менее двух графиков по результатам собственных экспериментов.

Первый график должен демонстрировать изменение времени выполнения или пропускной способности при изменении параметра модели.

Второй график должен показывать другую исследуемую характеристику:

-                время ожидания;

-                количество отказов;

-                загрузку ресурсов;

-                длину очереди;

-                распределение операций;

-                количество повторных попыток;

-                другой показатель, предусмотренный индивидуальным вариантом.

Для построения графиков допускается использование Python, MATLAB, R, Excel и других инструментов.

Не допускается представление графиков с вымышленными экспериментальными данными.

6.3. Анализ

Студент должен объяснить:

-                какие параметры изменялись;

-                какой результат ожидался;

-                какие результаты были получены;

-                как механизм синхронизации повлиял на работу модели;

-                почему изменение нагрузки не обязательно приводит к пропорциональному изменению производительности.

7. Требования к использованию Git

7.1. Общие положения

Использование системы контроля версий Git является обязательным.

Каждый студент выполняет лабораторную работу в индивидуальном репозитории.

Репозиторий создается до начала разработки и должен быть доступен преподавателю на протяжении всего периода выполнения работы.

Студент обязан регулярно отправлять результаты разработки в удаленный репозиторий.

Рекомендуется использовать закрытый репозиторий GitLab или GitHub с предоставлением доступа преподавателю.

7.3. Этапы разработки и контрольные точки

Разработка должна быть разделена на четыре контрольных этапа.

Этап 1. Проектирование.

Создание структуры проекта, описание архитектуры, определение общих ресурсов и разработка схемы взаимодействия участников.

Этап 2. Базовая реализация.

Создание процессов или потоков, реализация основных состояний и начальной логики модели.

Этап 3. Синхронизация и тестирование.

Добавление механизмов взаимного исключения, проверок инвариантов, обработки ошибок и тестов.

Этап 4. Эксперименты и отчет.

Проведение измерений, подготовка графиков, схем, анализа результатов и окончательного отчета.

Для каждого этапа необходимо создать содержательный коммит и отправить его в удаленный репозиторий.

При необходимости этап может содержать несколько коммитов.

Сроки контрольных точек устанавливает преподаватель. Преподаватель может фиксировать хеши коммитов, соответствующих каждой контрольной версии.

7.4. Требования к коммитам

Каждый коммит должен содержать логически завершенное изменение и понятное описание.

Примеры:

Создана базовая модель философов

Добавлена синхронизация через Mutex

Реализована проверка состояния вилок

Исправлено освобождение ресурса при тайм-ауте

Добавлено измерение времени ожидания

Добавлен скрипт построения графиков

Подготовлен отчет

Не допускается искусственное создание истории коммитов, не соответствующей фактической последовательности разработки.

После публикации контрольных версий запрещается без согласования с преподавателем:

-                удалять опубликованную историю;

-                изменять опубликованные коммиты;

-                выполнять принудительную перезапись основной ветки;

-                подменять контрольные версии.

Исправления необходимо фиксировать последующими коммитами.

Количество коммитов само по себе не является критерием самостоятельности.

7.5. Проверка истории разработки

Преподаватель вправе:

1.    Просмотреть историю коммитов.

2.    Сравнить любые две версии проекта.

3.    Попросить объяснить конкретное изменение.

4.    Попросить показать работу промежуточной версии.

5.    Проверить соответствие истории разработки представленному отчету.

6.    Попросить внести небольшое изменение и зафиксировать его новым коммитом.

История Git рассматривается как дополнительное свидетельство процесса разработки, но сама по себе не является доказательством авторства программного кода.

9. Приложения: исходные материалы для графиков, схем и диаграмм

Все графики, схемы, диаграммы и другие визуальные материалы должны сопровождаться исходными файлами, позволяющими воспроизвести их построение и при необходимости внести изменения.

В приложениях к отчету необходимо приводить:

-                исходный код Python, MATLAB, R и других программ, использованных для обработки данных и построения графиков;

-                исходные описания диаграмм PlantUML, Mermaid, Graphviz и аналогичных средств;

-                сведения об исходных редактируемых файлах draw.io и других графических редакторов;

-                экспериментальные данные, использованные для построения графиков;

-                дополнительные необходимые скрипты и конфигурации.

9.1. Требования к текстовым исходникам

Исходный код скриптов и текстовые описания диаграмм должны быть приведены в приложениях к отчету с сохранением форматирования.

Кроме того, соответствующие исходные файлы должны находиться в репозитории Git.

Пример:

Приложение А. Исходный код Python для построения графика зависимости времени ожидания от количества потоков.

Приложение Б. Исходный код PlantUML диаграммы последовательности.

9.2. Требования к графическим редакторам

Для схем, созданных в draw.io, Visio или аналогичных редакторах, необходимо:

1.    Включить схему в основную часть отчета.

2.    Указать инструмент создания.

3.    Указать имя исходного файла и путь к нему в репозитории.

4.    Предоставить сам файл в редактируемом формате.

Вставка полного XML-содержимого файла draw.io в текст отчета не требуется, если исходный файл предоставлен отдельно.

-                открыть исходную диаграмму;

-                изменить элементы схемы;

-                запустить скрипт построения графика;

-                получить график на основании предоставленных экспериментальных данных;

-                проверить соответствие исходников материалам отчета.

Предоставление только скриншотов или изображений не заменяет исходные файлы.

При отсутствии необходимых исходных материалов отчет считается неполным.

10. Использование моделей искусственного интеллекта

10.1. Общие положения

Использование моделей искусственного интеллекта допускается в качестве вспомогательного инструмента для:

-                изучения теоретического материала;

-                получения справочной информации;

-                объяснения Windows API;

-                анализа программного кода;

-                поиска и исправления ошибок;

-                разработки отдельных программных компонентов;

-                анализа экспериментальных результатов;

-                создания вспомогательных скриптов;

-                подготовки графиков и диаграмм.

Студент несет ответственность за корректность всех предоставленных материалов независимо от того, использовался ли при их создании искусственный интеллект.

Использование моделей ИИ не освобождает от необходимости самостоятельно понимать, объяснять, проверять и изменять программный код.

10.2. Обязательное декларирование

В отчете должно присутствовать отдельное приложение «Использование искусственного интеллекта».

Для каждого случая применения ИИ необходимо указать:

1. Инструмент и конкретную модель.

Указать название сервиса и точное обозначение модели.

Например:

-                ChatGPT – конкретная модель GPT;

-                Claude – конкретная модель;

-                Gemini – конкретная модель.

Если точная версия модели не отображалась в интерфейсе, необходимо указать доступное обозначение модели и отдельно отметить невозможность установить точную версию. Запрещается указывать предположительную версию как достоверную.

2. Цель использования.

Необходимо конкретно описать задачу, при решении которой применялись модели ИИ.

3. Оригинальный текст промпта.

Необходимо привести полный текст запроса, направленного модели ИИ.

Текст должен быть представлен без сокращений, исправлений или перефразирования.

Если решение получено в результате нескольких запросов, необходимо привести первоначальный и все относящиеся к решению уточняющие запросы в их исходной последовательности.

4. Полученный результат.

Кратко описать, что предоставила модель: объяснение, алгоритм, программный код, рекомендации, исправление ошибки, скрипт или другой материал.

5. Использование результата.

Указать, где именно использованы полученные материалы:

-                название файла;

-                название функции;

-                участок программного кода;

-                номер схемы;

-                номер графика;

-                раздел отчета.

6. Самостоятельная проверка.

Описать, как студент проверил полученный результат, какие изменения внес самостоятельно и каким способом убедился в его корректности.

12. Порядок защиты

Защита лабораторной работы включает четыре этапа.

Этап 1. Демонстрация программы

Студент запускает приложение и демонстрирует:

-                выполнение индивидуального задания;

-                создание участников модели;

-                работу механизмов синхронизации;

-                журнал событий;

-                результаты проверки корректности.

Студент должен объяснить:

-                особенности примененного механизма синхронизации;

-                причины принятого технического решения.

Этап 3. Практическое изменение

Преподаватель задает небольшое изменение существующей программы.

Например:

-                изменить максимальный тайм-аут;

-                добавить новый счетчик;

-                изменить количество участников;

-                добавить проверку инварианта;

-                изменить объем обрабатываемых данных;

-                дополнить журнал событий.

Студент должен внести изменение, выполнить сборку и продемонстрировать результат.

Изменение фиксируется новым коммитом.

Этап 4. Проверка экспериментальных материалов

Преподаватель вправе потребовать:

-                повторить один из экспериментов;

-                изменить параметры;

-                пересоздать график;

-                изменить исходную диаграмму;

-                объяснить экспериментальные результаты;

-                объяснить использование ИИ, если оно было заявлено.

Неспособность воспроизвести результаты или объяснить основные механизмы синхронизации свидетельствует о недостаточном освоении материала независимо от работоспособности предоставленной программы.

17. Индивидуальные варианты заданий

Каждый студент выполняет один вариант согласно своему номеру в списке группы.

Раздел А. Модель «Обедающие философы»

Общая модель: несколько философов располагаются за круглым столом. Между соседними философами находится одна вилка. Для приема пищи необходимо получить обе соседние вилки.

Один цикл философа:

THINKING → WAITING → EATING → THINKING

Каждый философ должен выполнить заданное количество циклов.

Для вариантов 1–6 стандартная конфигурация – пять философов по 100 циклов. Для варианта 7 используется семь философов.

Вариант 1. Упорядоченный захват ресурсов

Механизм: Critical Section.

Создать отдельную критическую секцию для каждой вилки.

Философ всегда должен захватывать сначала вилку с меньшим номером, затем с большим.

После приема пищи обе вилки освобождаются.

Исследовать:

-                5 и 7 философов;

-                длительность приема пищи 5 и 20 мс.

Определить среднее и максимальное время ожидания.

Проверить отсутствие одновременного использования вилки несколькими философами.

Вариант 2. Ограничение конкурентного доступа

Механизмы: Semaphore, Mutex.

Для каждой вилки создать Mutex.

Дополнительно использовать Semaphore, ограничивающий количество философов, которым разрешено одновременно пытаться получить вилки, значением N−1.

Сравнить:

-                алгоритм с ограничивающим семафором;

-                алгоритм с глобальным порядком захвата вилок.

Использовать 5 и 7 философов.

Оценить продолжительность ожидания ресурсов.

Вариант 3. Централизованный диспетчер

Механизмы: Critical Section, Condition Variable.

Разработать диспетчер, управляющий состоянием всех вилок.

Философ запрашивает у диспетчера сразу две вилки. Если обе доступны, диспетчер предоставляет их. В противном случае философ ожидает уведомления.

После завершения операции философ возвращает обе вилки.

Исследовать:

-                5 и 7 философов;

-                низкую и высокую интенсивность запросов.

Определить время ожидания и количество одновременно обслуживаемых философов.

Вариант 4. Асимметричный захват

Механизм: Mutex.

Философы с четными номерами сначала захватывают левую вилку, с нечетными – правую.

После получения обеих вилок выполняется прием пищи.

Исследовать:

-                5 и 7 философов;

-                продолжительность размышления 2 и 15 мс.

Проверить отсутствие взаимной блокировки в выполненных экспериментах и объяснить механизм её предотвращения.

Вариант 5. Захват с тайм-аутом

Механизм: Mutex.

Философ захватывает первую вилку, затем пытается получить вторую в течение заданного времени.

Если получить вторую вилку не удалось, он освобождает первую и повторяет попытку после небольшой задержки.

Исследовать тайм-ауты 5 и 50 мс.

Определить:

-                количество неудачных попыток;

-                среднее время ожидания;

-                общее время завершения модели.

Вариант 6. Справедливое распределение ресурсов

Механизмы: Critical Section, Event.

Создать центральную очередь запросов на получение вилок.

Запросы должны обслуживаться в порядке поступления. Если первый ожидающий запрос невозможно удовлетворить, последующие запросы не должны его обходить.

Сравнить:

-                обслуживание в порядке FIFO;

-                обслуживание без строгого соблюдения FIFO.

Определить распределение времени ожидания между философами.

Вариант 7. Ограничение числа одновременно обедающих

Механизмы: Semaphore, Mutex.

Для семи философов реализовать дополнительное ограничение количества одновременно обедающих.

При этом каждая вилка по-прежнему должна быть защищена отдельным Mutex.

Исследовать максимальное число одновременно обедающих:

-                1;

-                2;

-                3.

Определить пропускную способность модели и среднее время ожидания.

Раздел Б. Модель «Писатели–читатели»

Необходимо организовать конкурентный доступ к общим данным.

Читатели получают данные, писатели изменяют их.

Для проверки согласованности рекомендуется использовать структуру:

struct SharedData {

    int A;

    int B;

    int C;

    int version;

};
